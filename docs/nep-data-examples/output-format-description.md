# Структура `output`

Для обычной правки:

```text
<|marker_i|>{новый текст с одним <|user_cursor|>}<|marker_j|><|endoftext|>
```

Здесь `i` и `j` — схематические обозначения чисел, существующих во входе. Для обычной замены `i < j`.

Ответ означает: **заменить исходный диапазон между этими границами на новый текст**.

## Ответ для примера выше

```text
<|marker_1|>result = calculate(price, tax, discount)<|user_cursor|>
<|marker_2|><|endoftext|>
```

Результат применения:

```python
price = 100
tax = 0.2
discount = 10
result = calculate(price, tax, discount)
log(result)
print(result)
```

`log(result)` и `print(result)` не возвращаются моделью: они сохраняются из исходного текста. Курсор в ответе отмечает положение внутри нового фрагмента. Он не становится частью кода.

## Несколько соседних регионов

Ответ может охватывать диапазон от `marker_1` до `marker_3`, то есть оба региона из примера:

```text
<|marker_1|>result = calculate(price, tax, discount)
<|marker_2|>log(result, discount)<|user_cursor|>
<|marker_3|><|endoftext|>
```

Промежуточная граница допустима; номера обычного ответа должны строго возрастать. Она не создаёт отдельную операцию применения: парсер удаляет все внутренние маркеры и заменяет **один непрерывный диапазон между первой и последней границей**. Промежуточные маркеры можно не выводить, если первая и последняя корректно задают замену.

Если между двумя изменениями есть код, который нужно сохранить, он должен остаться в новом тексте охватывающего диапазона. Механизма независимых несмежных patch-операций в текущем `apply_completion()` нет.

## Вставка и удаление

Например, добавить строку после `log(result)` можно, сохранив саму строку в новом тексте второго региона:

```text
<|marker_2|>log(result)
notify(result)<|user_cursor|>
<|marker_3|><|endoftext|>
```

Удалить второй регион можно пустой заменой между **разными** границами:

```text
<|marker_2|><|user_cursor|><|marker_3|><|endoftext|>
```

Это удаление `log(result)\n`, **не no-op**. Примеры этой и следующей секций иллюстрируют разные операции над одним входом.

## No-op: ничего не менять

Каноническая явная запись:

```text
<|marker_1|><|user_cursor|><|marker_1|><|endoftext|>
```

Одинаковая граница дважды и отсутствие содержательного текста между ними означают no-op. Номер должен существовать во входе; это не обязательно `1`. Парсер допускает только whitespace вместо пустого содержимого в таком ответе, но канонический пример выше его не содержит.

Второй способ получить no-op — вернуть исходное содержимое диапазона без изменений, даже с разными границами. Поэтому поведение определяется **результатом применения**, а не только формой маркеров или JSON-полем `kind`.

No-op означает отсутствие изменения кода. Курсор протокола при сравнении кода удаляется.

# Обязательные проверки Output

- Ровно один `<|endoftext|>`, непосредственно в конце ответа.
- Не меньше двух границ; их номера существуют во входе.
- Ровно один курсор между первой и последней границей ответа.
- Для обычной замены номера строго возрастают; для явного no-op — две одинаковые границы и пустое/whitespace-тело после удаления курсора.
- Нет объяснений до или после рамки ответа. Текущий парсер терпит внешний whitespace перед первой/после последней границы, но после EOS ничего быть не должно.
- В replacement не допускаются зарезервированные NEP/FIM/chat-разделители.
- **Синтаксически допустимый NEP-ответ обязательно является кандидатом правильной правкой.** Проверки протокола, AST (синтаксиса), согласия с эталоном и смысла изменения — разные уровни.
