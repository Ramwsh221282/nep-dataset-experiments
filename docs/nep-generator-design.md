# CodeFinetuner: генератор данных для Next Edit Prediction

## 1. Результат изучения

В скачанной версии `generator/codefinetuner` исходный pipeline по-прежнему был FIM:

- `preprocess/extract.py` извлекал отдельные блоки `(bytes, node)`, теряя путь и состояние репозитория;
- `preprocess/process.py::_generate_fim_examples_from_code_block()` вырезал AST-подблок и формировал PSM FIM;
- `preprocess/config.py` и `process.py` были связаны с токенизатором/моделью;
- `pipeline.py` импортировал preprocess, обучение, оценку и конвертацию сразу;
- `tree_sitter_definitions.json` уже содержал 12 языковых профилей. Наличие грамматики само по себе не означает поддержку семантических NEP-преобразований.

Добавлен отдельный dataset-only модуль `src/codefinetuner/nep`. В проекте остаётся FIM Preprocess; обучение, оценка и конвертация моделей удалены.

**Это работающий консервативный MVP, а не полный многоязычный refactoring engine и не готовый промышленный корпус.** Ограничения покрытия приведены ниже. Обучение, токенизация, загрузка модели и внешние LLM API не нужны.

## 2. Контракт формата

Основание — документация `docs/nep-data-examples` (названия двух файлов про input/output инвертированы).

- JSONL: `id`, `input`, `output`.
- Input: SPM, `fim_suffix → fim_prefix → контекст → edit_history → текущий файл → fim_middle`.
- История содержит уже выполненные действия, в хронологическом порядке от старых к новым.
- Маркеры `1…N` — соседние границы, не номера строк и не независимые пары.
- Output заменяет **один непрерывный диапазон**. При несмежных изменениях неизменённый промежуток нужно сохранить в replacement.
- Курсор входа может быть выше/на месте/ниже изменения; он не задаёт разрешённый диапазон.
- Удаление — пустая замена между разными границами. No-op — две одинаковые границы с курсором.
- Невалидный промежуточный код допустим. Валидность протокола, синтаксиса, типов и поведения проверяется раздельно.

`protocol.py` реализует SPM-сериализацию, разбор и применение ответа. Проверяется равенство `apply(input, output) == target_after`, включая Unicode, CRLF, конец файла без newline, пустые файлы, удаления, no-op и сохранение промежутков. Контекст и история не становятся частью целевого файла. Зарезервированные разделители в исходниках отклоняются, а не экранируются с изменением кода. Десять приложенных JSONL-примеров также разбираются этим валидатором.

Редактируемое окно строится по строкам вокруг правки: сама правка и по одной соседней строке, если они существуют. Неизменяемый префикс остаётся в текущем файле, хвост переносится в suffix. Не делается скрытой обрезки длинного примера: он отбрасывается по символьному бюджету. Это **не токенный лимит**; перед обучением нужна проверка конкретным токенизатором.

## 3. Причинная история: состояния, а не декоративные diff

```text
S0 --e1--> S1 --e2--> S2 ... --et--> St --next_edit--> St+1
                                    |                  |
                              input + history       output
```

`Scenario` содержит:

- `initial`: снимок файлов до истории;
- `history`: реальные `Step(path, before, after)`;
- `target_path`, `target_after`: следующий целевой файл и его состояние;
- `kind`, `language`, `family_id`.

`replay()` проверяет каждый `before`, запрещает фиктивные шаги и восстанавливает `St`. Unified diff строится **из этих же шагов**, а контекст — только из `St`. Будущая правка не добавляется в историю и не выдаётся как «уже актуальный» контекст целевого файла. История может содержать исходный код удалённого элемента: это необходимая информация о прошлом, не утечка будущего ответа.

Одна исходная версия обычно является финальным состоянием синтетической траектории. Для переименования генератор реконструирует предыдущую согласованную версию и последовательно возвращает правильные имена. Для удаления исходная версия, наоборот, является началом траектории удаления функциональности.

### Пример: межфайловое переименование

Исходный снимок:

```python
# provider.py
def calculate(x):
    return x + 1

# consumer.py
import provider
first = provider.calculate(1)
second = provider.calculate(2)
```

Траектория:

1. `S0`: определение и оба вызова имеют имя `calculate_nep`.
2. `e1`: разработчик переименовал определение в `calculate`.
3. Первый пример: актуальный provider содержит `calculate`, история показывает `e1`; ответ меняет первый зависимый вызов.
4. `e2`: первый вызов исправлен.
5. Второй пример: история `e1,e2`; ответ меняет второй вызов.
6. При `--include-noop` — завершённая траектория без следующего изменения.

Это последовательные next-edit примеры, а не повторная выдача уже применённого diff. В промежуточных состояниях могут оставаться другие старые употребления: один ответ не обязан завершать весь рефакторинг.

### Важная оговорка о причинности

Проигрываемость доказывает согласованность состояний, но **не доказывает**, что обученная модель использует историю. Структурное дополнение выражения часто решаемо только по текущему коду — это completion-подмножество, а не доказательство полноценного NEP.

Для исследования использования истории нужны отдельные контрфактические пары: одинаковые текущий файл и курсор, разные допустимые предыстории/актуальный внешний контекст, разные следующие правки. Например, два направления миграции API, меняющие один и тот же устаревший вызов по-разному. Их нельзя получать простой случайной перестановкой истории: нарушится согласованность состояния. В текущем MVP автоматическая генерация таких пар и обучение/ablation **не реализованы**. Рекомендуемые проверки: full context против no-history, no-cross-file-context и согласованной альтернативной истории; exact edit, применимость, compiler/typecheck, доля неправильных no-op.

## 4. Несколько вариантов из одного файла

| Класс | Что реализовано | Ограничения |
|---|---|---|
| `insert` | AST/CST-выражение вводится частями; история содержит предыдущие префиксы, ответ дописывает выражение | Только подходящие однострочные выражения 4–512 байт; не выдаётся за семантическую миграцию |
| `replace` локально | Переименование параметра и последовательное обновление его употреблений | Python, узкая приватная функция без внешних обращений, вложенных областей, rebinding, reflection, debug f-string и др. |
| `replace` межфайлово | Переименование определения и поочерёдное обновление `module.function(...)` | Только простой однозначный Python import, см. следующий раздел |
| `delete` | В истории удалено определение; следующий edit удаляет зависимый standalone-вызов | Python: приватная функция без параметров и единственное прямое употребление; результат вызова не используется; строки с именем, imports, dynamic lookup и ряд неоднозначностей отклоняются |
| `noop` | Все шаги выбранной синтетической задачи завершены | По умолчанию выключен: завершение синтетической задачи не доказывает намерение человека ничего не менять |
| Положение курсора | Для одной правки создаются `above`, `at`, `below`, где есть соответствующие строки | Метка описывает курсор относительно правки; одинаковый input/output дедуплицируется |
| Префиксы истории | Несколько шагов одной траектории образуют несколько обучающих примеров | Общий `family_id`; нельзя разносить между train/eval/test |

**Не каждый файл обязан давать все типы.** Если нет безопасного определения/употребления или подходящего выражения, соответствующий пример не создаётся. Лимит на файл может остановить перечисление до поздних классов; распределение нужно контролировать по отчёту, а не считать автоматически сбалансированным.

Удаление трактуется как **удаление функциональности**, а не semantics-preserving оптимизация: эффекты удаляемого вызова могут намеренно исчезать. Для безопасного автоматического refactoring требовалась бы отдельная проверка эффектов. Нельзя автоматически удалять `result = removed_function()` или произвольный аргумент вызова: нужно восстановить data flow и намерение пользователя. Таких примеров генератор не создаёт.

### Полезные дальнейшие сценарии

1. Изменение сигнатуры: добавление/удаление аргумента → обновление вызова; значение нового аргумента должно быть выводимо из scope/истории.
2. Изменение возвращаемого типа/структуры → обновление чтения поля и destructuring.
3. Изменение схемы/enum → обновление конструктора, сериализатора и `switch/match`.
4. Перенос символа → import migration и изменение квалификатора.
5. `sync → async` → `await` и последующее распространение async, с проверкой типов.
6. Удаление ветки feature flag → очистка связанных веток/импортов, не произвольное удаление зависимого кода.
7. Изменение implementation → соседняя проверка/тест по новому контракту.
8. Исправление синтаксиса после реально смоделированных keystroke-состояний.
9. Два разнесённых изменения в одном допустимом диапазоне с сохранением кода между ними.
10. Согласованное продолжение локального стиля обработки ошибок/логирования, только если намерение достаточно определено историей.

Эти сценарии — **план расширения**, не реализованные возможности. Для каждого нужны preconditions, transform, resolver, replay, валидатор и тесты отрицательных случаев.

## 5. Межфайловый контекст и границы разрешения символов

MVP разрешает только:

- корневые `provider.py` и `consumer.py`;
- единственный прямой `import provider` первым statement, без alias/from/star;
- provider из одной недекорированной функции без сложных зависимостей;
- consumer с прямыми `provider.function(...)` в простых top-level statements;
- отсутствие shadowing, collision, дополнительных неоднозначных обращений/пакета с тем же именем, строковых/динамических ссылок и сторонних потребителей в снимке.

Это намеренно значительно уже обычного Python. `from ... import ...`, пакеты, LSP, перегрузки, пользовательский import machinery, алиасы, динамический dispatch и межфайловое удаление **не поддерживаются**. Предполагается обычное разрешение импорта из выбранного source root.

В prompt попадают только причинно выбранные внешние файлы, затронутые историей. Случайные соседние файлы не добавляются. Нет общего поиска релевантного контекста для completion-примеров. Следующий этап — repository index с определениями, imports, usages и confidence. Дальние зависимости следует включать выдержками с исходными путями/диапазонами и жёстким бюджетом, но не удалять из prompt необходимую причину target.

Если при чтении пропущены поддерживаемые файлы из-за размера, кодировки, separator collision, symlink или непроверенные каталоги, CLI отключает семантические сценарии для всего снимка. Иначе пропущенный пакет мог бы сделать импорт неоднозначным. Служебные `.git`, окружения и `__pycache__` не считаются исходниками. Это консервативный барьер, не доказательство полноты произвольного динамического проекта. Для Python API `generate_scenarios(files)` вызывающая сторона отвечает за полноту снимка; при сомнениях передать `allow_semantic=False`.

## 6. Языки: парсер ≠ семантика

| Уровень | Языки | Реализованная возможность |
|---|---|---|
| CST | Python, JavaScript/JSX, TypeScript, TSX, Java, C, C++, Go, Rust, C# | Извлечение выражений, структурное инкрементальное дополнение, проверка синтаксиса полного target |
| Ограниченный semantic | Python | Локальный rename, delete, узкий cross-file rename |
| Будущие adapters | Остальные языки | Scope/binding/import resolution, language-specific transformations, compiler/typechecker |

`languages.py` задаёт расширения и capability tiers. `.h` по умолчанию C; проектные C++ headers требуют отдельной настройки, которой пока нет. Валидность CST для Java/C#/TypeScript не означает прохождение компилятора или typechecker. Регистрация грамматики не должна автоматически включать rename/delete. Тестовые fixtures проверяют структурную генерацию на каждом указанном языке, не полное покрытие его синтаксиса.

Tree-sitter использует UTF-8 byte offsets. Engine редактирует bytes; сериализатор использует Unicode character offsets уже восстановленных строк. Смешивать эти системы нельзя.

Для развития предпочтителен `LanguageAdapter` с `parse`, `definitions`, `references`, `resolve_import`, `safe_transform`, `validate`. Источники семантики: Python AST+symbol tables, TypeScript compiler API, rust-analyzer, gopls/go-types, clangd/compile_commands, JDT/Roslyn. Не нужно заменять resolver глобальным regex-переименованием.

## 7. Запуск без обучения и без GPU

Из `generator/codefinetuner`:

```sh
uv venv .venv-nep --python 3.12
uv pip install --python .venv-nep/bin/python -r requirements-nep.txt
PYTHONPATH=src .venv-nep/bin/python -m codefinetuner.nep \
  /absolute/path/to/source-repository outputs/nep-run \
  --repository-id organization/project --split train
```

`/absolute/path/to/source-repository` и `organization/project` заменить на свой репозиторий и его стабильный идентификатор. Output должен быть новой/пустой директорией. Код источника не изменяется. Для независимого запуска NEP доступен лёгкий путь через отдельный requirements и `PYTHONPATH`, как выше.

Совместимые версии tree-sitter и TS/C# bindings закреплены в `requirements-nep.txt`: новые bindings несовместимы с исходной веткой tree-sitter 0.22. Генерация выполняется локально, без отправки кода и API-расходов; установка зависимостей может требовать сеть.

Параметры:

- `--max-scenarios-per-file 30` — число базовых сценариев до cursor augmentation, включая перечисленные no-op до их фильтрации;
- `--max-file-bytes 100000`, `--max-files 1000` — ограничения snapshot;
- `--max-example-chars 24000` — общий символьный бюджет input+output;
- `--include-noop` — опциональное включение завершённых синтетических траекторий;
- `--split train|eval|test` — явно назначенный split всего репозитория.

Артефакты:

- `train.jsonl` (либо `eval.jsonl` / `test.jsonl`) — только `id/input/output`;
- `audit.jsonl` — initial вовлечённых файлов, полная история, target, family, cursor, repository id и hash снимка; позволяет пересобрать пример;
- `report.json` — counts по языкам/операциям/курсору, причины пропуска, бюджеты и доступность semantic-сценариев.

Audit содержит исходный код и эталоны: хранить с теми же ограничениями доступа, что и репозиторий; **не подавать в модель как входной контекст**. Он может быть заметно больше обучающего JSONL.

## 8. Разбиение и качество корпуса

Split назначается **репозиторию до генерации**, не отдельным строкам, файлам или сценариям. Все его версии и синтетические варианты должны оставаться в одном split. CLI не ведёт глобальную базу назначения: при нескольких запусках это ответственность orchestrator. Идентичные input/output удаляются внутри одного запуска, но дедупликация форков и клонов между запусками пока отсутствует.

Перед масштабным обучением нужны:

1. Repository/revision/family-disjoint splits и межрепозиторная дедупликация.
2. Баланс insert/replace/delete/no-op; не дать дополнениям численно превратить задачу обратно в FIM.
3. Баланс расположения правки относительно курсора и глубины истории.
4. Исключение generated/vendor/secrets/licensing-incompatible источников по проектной политике. Текущий reader не является secret scanner и не разбирает `.gitignore`.
5. Реальные compiler/typecheck/test gates там, где доступны; текущий инструмент исходный код не исполняет.
6. Контрфактические пары и ablation истории/контекста.
7. Реальные IDE editing traces: Git-коммит показывает итог, но не восстанавливает единственную истинную последовательность действий разработчика. Синтетические траектории нужно маркировать как synthetic (в данном MVP все сценарии синтетические).
8. Проверка tokenizer/max length и корректная loss mask: обучать ответ, не историю/контекст.
9. Разнообразные имена для inverse rename вместо заметного `_nep`-артефакта. Текущий суффикс удобен для аудита, но создаёт shortcut; не стоит обучать production-модель только на этих примерах.

## 9. Тесты

```sh
uv pip install --python .venv-nep/bin/python pytest
PYTHONPATH=src .venv-nep/bin/python -m pytest tests/nep -q
```

Проверяются языковые fixtures, replay/детерминизм, неоднозначные bindings, unsafe удаления, Unicode, cross-file история, SPM/маркеры/EOS, исходные 10 примеров, cursor variants, audit round-trip, budget rejection, защита от overwrite, неполный snapshot и отсутствие импортов training stack.

FIM-тесты запускаются отдельно и требуют зависимости preprocessing и локальный tokenizer fixture; веса модели для NEP не нужны. Сам факт прохождения тестов не заменяет оценку разнообразия и семантической точности большого корпуса.
