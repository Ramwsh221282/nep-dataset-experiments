# План улучшения NEP-генератора

Статус: **план, не реализованные возможности**. Основан на проверке текущих
`engine.py`, `protocol.py` и десяти примеров из `online-diary-backend-rust`.
Область работ — исключительно генерация, валидация и сохранение данных. Обучение
моделей, инференс и конвертация весов не возвращаются.

## 1. Диагноз

1. `_insertions()` выбирает несколько символьных срезов однострочного выражения.
   История удлиняет обрезанный текст, а target сразу восстанавливает всё выражение.
   Это восполнение пропуска, не предсказание следующего синтаксического действия.
2. Генератор требует синтаксически допустимый полный target. Поэтому не может
   последовательно выдавать `usersRepository`, затем `.getUser`, затем аргументы,
   если на промежуточной стадии файл ещё не парсится.
3. Rename/delete реализованы только для узких Python-случаев. Rust-парсер есть,
   но Rust-разрешения символов и зависимых преобразований нет.
4. Изменение положения курсора не добавляет новый стиль input: один и тот же
   обрезанный исходник остаётся задачей дополнения при любом положении курсора.
5. `Step` хранит before/after целого файла, но нет явной модели локальных edits,
   действий разработчика, атомарных групп изменений и графа зависимостей.
6. `render()` выводит границы из эталонной правки и работает по строкам. Нужны
   пустые диапазоны, внутристочные границы и окно, определяемое текущим состоянием,
   а не подсказкой о местоположении заранее известного ответа.
7. Число шагов истории, число изменённых участков и число маркеров смешиваются
   при оценке разнообразия. Это независимые характеристики.
8. Нет квот по типу состояния input, глубине истории, операциям и наличию
   межфайловой причины. Первые подходящие примеры могут занять весь лимит.

## 2. Целевое поведение

Генерировать не «исходник с дыркой», а **сценарий редактирования проекта**:

```text
Исходное состояние → действие → состояние → действие → состояние …
                                      └→ input текущей точки → следующий action
```

Каждый пример должен содержать уже выполненную историю и следующий шаг, который
ещё не применён. Шаг может:

- дописать целый синтаксический элемент после завершённого идентификатора;
- изменить полностью написанный код из-за предыдущего действия;
- исправить несколько зависимых участков одного файла;
- удалить ставший ненужным аргумент, импорт или вызов;
- оставить код без изменений, если выбранная задача уже закончена.

Реалистичное состояние input важнее искусственного разнообразия оформления.
Типы input: partial identifier, boundary after identifier, incomplete expression,
complete-but-stale code, partially migrated file, completed task. Фиксировать их
раздельно в audit. Парсируемость не равна актуальности: `getUser(id, name)` может
быть синтаксически корректным, но не соответствовать новой сигнатуре.

## 3. Два семейства, которые нельзя смешивать

### A. Инкрементальное построение

Для полного выражения `await usersRepository.getUser(id, name);` выделять
действия по CST/токенам, а не по процентам длины строки:

| Текущее состояние | Следующий добавляемый фрагмент |
|---|---|
| `await` | ` usersRepository` |
| `await usersRepository` | `.getUser` |
| `await usersRepository.getUser` | `(id, name)` |
| `await usersRepository.getUser(id, name)` | `;` |

В каждом случае target — результат **одного следующего действия**, не финальное
выражение. Каждый полученный шаг может затем войти в историю следующего примера.
Границы действия не обязательно совпадают с одним токеном: `.getUser`, список
аргументов или блок могут быть единым редакторским действием. Значимые пробелы,
отступы и переводы строк сохраняются точно.

Слой синтаксических частей должен учитывать идентификаторы, member access,
qualified paths, вызовы, аргументы, `await`, Rust `.await`, `?`, `::`, литералы,
разделители, переносы и блоки. Приоритет: member access/call chains и аргументы.
Unicode не режется внутри кодовой точки; комментарии и строки не разбиваются
так же, как идентификаторы. Rust macro token trees требуют отдельной поддержки.

**Два разных случая точки с запятой:**

- Если `;` уже находится в suffix, она сохраняется и не появляется повторно в
  output. Тогда последний шаг таблицы отсутствует.
- Если `;` ещё не введена, она входит в траекторию отдельным действием и не может
  заранее находиться в suffix.

Короткая вставка между двумя разными маркерами в одной текстовой позиции должна
поддерживаться явно. Пример ниже — продолжение сценария, где developer уже
добавил объект; история соответствует текущему файлу:

```text
<|fim_suffix|>;
<|fim_prefix|><|file_sep|>edit_history
--- a/src/users.ts
+++ b/src/users.ts
@@ -1 +1 @@
-await;
+await usersRepository;
<|file_sep|>src/users.ts
await usersRepository<|marker_1|><|user_cursor|><|marker_2|><|fim_middle|>
```

Ответ следующего шага:

```text
<|marker_1|>.getUser<|user_cursor|><|marker_2|><|endoftext|>
```

Используются канонические разделители проекта: `<|fim_suffix|>`, а не
`<[fim-suffix]>`; курсор и EOS обязательны. Этот пример демонстрирует сериализацию,
а достаточный контекст API для выбора `getUser` нужно добавлять отдельно.

Для первой точки траектории нужна настоящая предыстория из сценария. Не добавлять
фиктивный diff только ради обязательной секции истории. Если её нет — пропускать
эту точку либо отдельно согласовать формат примеров с пустой историей.

### B. Продолжение изменения контракта

Input не обрезается. Разработчик уже изменил определение, но зависимый код ещё
остался прежним:

```diff
# Уже произошло в файле определения:
-getUser(id, name)
+getUser(id)
```

Текущий целевой код:

```ts
const user = await usersRepository.getUser(id, name);
```

Следующий edit:

```ts
const user = await usersRepository.getUser(id);
```

Это **миграция сигнатуры с удалением аргумента**, а не переименование. Rename —
отдельный сценарий, например `getUser → findUser`, после которого меняются usages.
Оба семейства нужны независимо от incremental construction.

Для удаления параметра надо проверить тело определения, соответствие аргументов,
overloads/defaults/rest/named arguments и разрешение вызываемого символа. Нельзя
безусловно превращать `getUser(id, sendNotification())` в `getUser(id)`: исчезает
побочный эффект. Такие случаи в первой версии пропускать. Даже чтение аргумента
не всегда безвредно (getters/proxies, Rust move/Drop); разрешать только проверенные
простые случаи либо явно моделировать изменение поведения, а не обещать его
сохранение. В Rust отдельно учитывать ownership и методы traits.

## 4. Что означает «несколько изменений»

### 4.1. Несколько действий в истории

Например:

1. Переименовано определение.
2. Исправлен первый вызов.
3. Исправлен второй вызов.
4. В input остаётся третий устаревший вызов; output исправляет его.

Генерировать разные префиксы истории, включая 1, 2–3, 4–8 действий. Это реальные
последовательные изменения состояния, не повтор одного diff и не случайный шум.

### 4.2. Несколько edits в одном следующем действии

Например, обновить два вызова в одном файле:

```diff
-let a = repo.getUser(idA, nameA);
+let a = repo.getUser(idA);
 log(a);
-let b = repo.getUser(idB, nameB);
+let b = repo.getUser(idB);
```

Внутри движка это два непересекающихся edit. В текущем NEP-протоколе ответ —
**одна замена охватывающего диапазона** с сохранённой строкой `log(a);` между ними.
Внутренние маркеры допустимы, но не становятся независимыми patch-операциями.

Далёкие участки не объединять ценой огромного ответа: если окно или бюджет не
позволяют сохранить промежуток, разбить миграцию на последовательные примеры.
При подсчёте разнообразия фиксировать edits/hunks, а не количество маркеров.

### 4.3. Несколько файлов

История и контекст могут включать несколько файлов. Один output текущего формата
редактирует только один целевой файл. Межфайловая миграция раскладывается на
следующие друг за другом однофайловые действия; предыдущие действия уже входят в
историю. Одновременный multi-file output потребовал бы версии протокола и сейчас
не планируется.

### 4.4. Выбор размера следующего действия

Точный конец «следующего edit» не всегда выводим из input: человек может обновить
один вызов или несколько. Нельзя считать все такие альтернативы ошибочными.

Для первой версии задавать одну детерминированную политику на семейство: incremental
construction — следующая синтаксическая часть; local propagation — один usage;
coherent local migration — все связанные usages внутри выбранного AST-блока.
Дедуплицировать одинаковые input с противоречивыми targets. Не создавать для одного
input одновременно single-edit и batch-edit эталоны без явной политики множества
допустимых ответов. Метка в audit сама по себе не объясняет модели эту разницу.

## 5. Новая внутренняя модель

Сохранить проверенный формат JSONL `id/input/output`, расширить внутреннюю модель:

- `RepositorySnapshot`: состояние файлов в конкретной точке.
- `TextEdit(path, start_byte, end_byte, replacement)`: локальная операция.
- `EditAction`: одно действие с одним или несколькими edits; фиксирует гранулярность
  и положение курсора до/после. Для экспортируемого next action — один target file.
- `Trajectory`: последовательность actions с начальным и конечным состояниями.
- `Dependency`: definition → usage, signature → call, declaration → import и т. п.
- `ScenarioMetadata`: семейство, тип input, synthetic/trace origin, причины выбора
  контекста, уровень разрешения символов и результаты проверок.

У каждого action координаты относительно явно указанного before-состояния.
Непересекающиеся edits применяются атомарно с конца файла; после action координаты
пересчитываются. Отдельно тестировать пересечения, одинаковые позиции вставки,
Unicode, CRLF и отсутствие завершающего newline.

В audit добавить `scenario_type`, `input_state_type`, `action_granularity`,
`history_action_count`, `history_edit_count`, `next_edit_count`, `next_hunk_count`,
`context_paths`, `dependency_kind`, `cursor_relation`, `syntax_status`,
`validation_level`, `skip_reason`, `trajectory_id`, `family_id`, `repo_id`.
Метаданные не подставляются в модельный input вместо фактических доказательств.

## 6. Языки и межфайловый контекст

### Два уровня адаптеров

1. **Syntax adapter:** CST, безопасные синтаксические границы, incremental
   construction, позиции маркеров. Реализуется для уже поддерживаемых грамматик.
2. **Semantic adapter:** символы, области видимости, imports, definitions/usages,
   типы получателя вызова, сигнатуры и разрешённые преобразования.

Для текущего Rust-проекта приоритет — Rust adapter: Cargo workspace/modules,
`use`, пути, функции, методы `impl` и разрешённые call sites. Практичный источник
семантики — rust-analyzer; для `usersRepository.getUser(...)` в TypeScript —
TypeScript compiler API с учётом `tsconfig` и module resolution. Tree-sitter
остаётся источником структуры, не заменяет разрешение символов.

Адаптеры должны работать на изменяемом snapshot: нельзя брать references/LSP edits
от дискового исходника и применять к другой синтетической версии с устаревшими
координатами. Использовать изолированную копию/виртуальные документы и версионные
symbol anchors. При incomplete index/неоднозначности — объяснимый skip, а не
лексический поиск совпадений. Динамический dispatch, macros, trait ambiguity,
re-exports и generics расширять отдельными capability-флагами и тестами.

Получать контекст по зависимостям: актуальная сигнатура/определение, imports,
необходимые типы, затронутые предыдущими actions фрагменты. Для autocomplete после
полного идентификатора также нужен контекст доступных members. Не добавлять
случайные соседние файлы. Не класть туда будущую исправленную версию целевого кода.
Если необходимая причина не помещается в бюджет — пропустить пример либо сузить
его логическую задачу, а не оставлять необъяснимый target.

Сборочные `target/`, vendor/generated и секреты исключать в основном reader, не
только в разовом скрипте выборки. Исключённый файл не доказывает отсутствия usages;
полноту индекса оценивать отдельно от того, что разрешено сериализовать в dataset.

## 7. Приоритетные сценарии

| Приоритет | Сценарий | Что объясняет следующий edit |
|---|---|---|
| P0 | Следующая синтаксическая часть | Уже введённая цепочка и доступный API/context |
| P0 | Переименование локального символа | Начатая согласованная rename-траектория |
| P0 | Переименование метода/функции | Изменённое определение и resolved usages |
| P0 | Удаление параметра | Новая сигнатура и устаревший вызов |
| P0 | Обновление нескольких usages в блоке | Единая локальная миграция |
| P1 | Добавление/перестановка параметров | Изменённая сигнатура; значение/порядок однозначно выводимы |
| P1 | Удаление feature-вызова/импорта | Явно смоделированное удаление функциональности |
| P1 | Изменение поля struct/DTO | Новая структура и зависимые constructors/readers |
| P1 | Перемещение символа | Новое определение и imports/qualified paths |
| P2 | `.await`, `?`, Result/Option migration | Проверенное изменение контракта и зависимых мест |
| P2 | Наблюдаемые editing traces | Реальный порядок действий с разрешением использования |

Для каждого сценария обязательны: preconditions, операция построения согласованного
S0, действия, extractor примеров, validator и отрицательные fixtures. Нельзя
получать «предысторию» заменой имени только в одном произвольном месте.

Статический исходник может служить конечной согласованной версией: например,
создать старую сигнатуру с безопасным неиспользуемым параметром и согласованными
вызовами, затем проиграть её удаление. Это synthetic trajectory, не фактическая
история автора. Аналогично inverse rename должен охватывать все доказанные usages
начального состояния и исключать name collisions. Не использовать постоянный
суффикс `_nep` как подсказку о том, какое имя нужно исправить.

## 8. Валидация, необходимая для новых примеров

### Всегда

- Replay `S0 + history == St`, отсутствие фиктивных действий.
- Применение output к St в точности даёт предусмотренный next state.
- Нет edits вне разрешённого окна; промежутки между edits сохранены.
- Контекст соответствует St, а не финалу траектории.
- Все курсоры, границы, EOS и SPM соответствуют действующему протоколу.
- Новое состояние не обязано сразу совпадать с оригинальным файлом: это верно
  только для последнего шага реконструкции, не для каждого incremental action.

### Incremental construction

Отменить глобальный фильтр «target должен целиком парситься». Промежуточные
состояния могут быть незавершёнными, но должны в точности соответствовать шагу
проверенной траектории. Проверять границы синтаксических частей на финальном CST,
локализацию ожидаемой незавершённости и парсируемость завершённой конструкции.
Нельзя просто отключить все проверки синтаксиса для всех семейств.

### Зависимые преобразования

Проверять resolved symbols и preconditions. Финальная миграция должна проходить
проверку сигнатур/references, по возможности compiler/typechecker. На промежуточном
шаге допустимы ожидаемые ошибки оставшихся stale usages, но не новые посторонние
ошибки. Сравнивать diagnostics с baseline и планом оставшихся изменений.

`cargo check`/compiler hooks не возвращают код обучения. Но запуск build scripts,
proc macros и загрузка зависимостей — выполнение чужого кода/сетевые действия:
использовать opt-in sandbox, offline-политику, timeout и изолированную копию, не
запускать автоматически при простом чтении репозитория.

### Проверка причинности

Сам факт наличия history недостаточен. Добавить согласованные контрольные пары:

- одинаковый target file и cursor;
- разные допустимые предыстории API и актуальный внешний context;
- разные ожидаемые правки вызова.

Например, из `getUser(id, name)` одна миграция удаляет второй параметр, другая —
первый; при доказанном сопоставлении аргументов получаются разные outputs.
Для history-only пары нужны одинаковые видимые current/context и различимая
предыстория, действительно задающая разное намерение; не подменять это случайным
shuffle diff. Проверять состояния конструктивно. Использует ли историю будущая
модель — отдельный вопрос downstream-оценки, а не гарантия генератора.

## 9. Баланс и честный отчёт

Стартовый целевой профиль, не утверждение о достижимом покрытии любого проекта:

| Семейство | Доля |
|---|---:|
| Дополнение части идентификатора | 10% |
| Следующая синтаксическая часть после законченного элемента | 25% |
| Rename propagation | 25% |
| Миграция сигнатуры | 25% |
| Удаление/очистка зависимого кода | 10% |
| Завершение задачи/no-op | 5% |

Дополнительные независимые цели: не менее 50% input с целыми идентификаторами и
завершённым, но устаревшим кодом; минимум 25% non-noop примеров с несколькими
локальными edits; минимум 30% примеров с необходимым межфайловым контекстом там,
где resolver обеспечивает покрытие. Следить за историей 1/2–3/4–8 действий и
правками выше/на/ниже курсора. Семейства и оси не складывать в одну таблицу процентов.

Отбор — по квотам и seeded sampling, не первые N генераций. Недоступную квоту
показывать как дефицит со skip reasons; не заменять молча всё вставками. Ограничить
число почти одинаковых префиксов/курсоров одной семьи. No-op не размножать после
каждого выражения: законченная конструкция ещё не доказывает отсутствие следующего
действия; использовать его только для явно ограниченных завершённых задач.

Окно редактирования и курсор выбирать из текущего snapshot/истории по заранее
заданной политике до рассмотрения target. Если next edit вне окна — пропускать или
выбирать другую точку траектории, а не раскрывать его позицию идеальными маркерами.
При вариации курсора не создавать невозможную последовательность действий.

Все trajectories/families/revisions одного репозитория остаются в одном split.
Одинаковые input с разными targets выявлять отдельно от точных дубликатов. Нужен
глобальный manifest split assignment при нескольких запусках, а не только CLI-флаг.

## 10. Этапы внедрения и критерии готовности

### Этап 1 — контракт траекторий и протокол (P0)

- Выделить `TextEdit`, `EditAction`, `Trajectory` из монолитного engine.
- Ввести action granularity и счётчики history/next edits.
- Поддержать пустые и внутристочные диапазоны в renderer.
- Сохранить непрерывный однофайловый output; добавить multi-hunk round-trip tests.
- Разделить валидацию incremental и semantic семейств.

**Готово, когда:** каждый шаг replayable; вставка `.getUser` возможна без выдачи
всего выражения; два изменения сохраняют нетронутый промежуток; `;` не дублируется;
промежуточный непарсируемый target не отбрасывается как обычная syntax failure.

### Этап 2 — синтаксическая инкрементальность и sampling (P0)

- Заменить `_insertions()` на chunk-based trajectory builder, оставив редкий
  subtoken-режим отдельно.
- Поддержать вызовы, цепочки, аргументы и разделители для Rust и TS/JS сначала.
- Добавить quotas, `--max-examples`, seed, coverage/skip report.
- Перенести правила исключения generated/target в общий reader.

**Готово, когда:** есть несколько последовательных next-step примеров одной цепочки;
input не ограничен половиной слова; выборка воспроизводима и реально соблюдает
доступные квоты. Этот этап улучшает construction, но сам по себе не закрывает NEP.

### Этап 3 — Rust semantic adapter + rename/signature migration (P0)

- Индекс Cargo workspace и версионные definitions/usages.
- Сначала локальные bindings и прямые функции; затем однозначные inherent methods.
- Rename и remove-parameter с безопасными preconditions.
- Актуальный межфайловый контекст; последовательное обновление usages.
- Негативные tests на shadowing, одинаковые имена разных типов, traits/macros,
  неполный индекс, argument effects и ownership.

**Готово, когда:** на завершённом Rust-input генерируются зависимые replace/delete,
и хотя бы часть — межфайловые; все семантические допущения отражены в audit.
Если конкретный проект не содержит безопасных случаев, report объясняет пропуски.

### Этап 4 — multi-edit и TypeScript-контракт (P0/P1)

- Одно действие обновляет несколько usages в одном AST-блоке.
- TS compiler adapter для примера `usersRepository.getUser` и сигнатур.
- Строгая дедупликация противоречивых granularities.
- Контрфактические тестовые пары и проверка зависимости от контекста.

**Готово, когда:** single/multi-edit, same/cross-file причины и 2–8 history actions
представлены тестами и демонстрационной выборкой без изменения JSONL-протокола.

### Этап 5 — дополнительные миграции и расширение языков (P1/P2)

- Добавление/перестановка аргументов, imports, поля структур, return types.
- Другие semantic adapters по реальным источникам данных, не по наличию грамматики.
- Опциональный импорт реальных editing traces с provenance и политикой приватности.

### Рекомендуемая следующая контрольная выборка

После этапов 1–4 сделать **30 примеров**, не только десять:

- 3 subtoken insertion;
- 7 chunk-level incremental (несколько последовательных шагов цепочек);
- 8 rename propagation;
- 8 signature migration;
- 3 зависимых удаления;
- 1 завершённый no-op.

Пересекающиеся критерии: ≥8 multi-edit; ≥10 history с 2+ действиями;
≥8 с внешним контекстом; ≥15 на завершённом устаревшем коде; позиции правок по обе
стороны курсора. Проверить на `online-diary-backend-rust`, TS-кейс пользователя —
на отдельном явно обозначенном fixture. Не выдавать fixture за реальный код проекта.
Если Rust-покрытия недостаточно, показать честный дефицит вместо подмены классов.

Результат: JSONL, audit, coverage report и Markdown, где для каждого примера видно
**что уже изменено → почему следующий edit нужен → какие участки он меняет**.
